- Do not comment your code the code that you generate must be self documenting and have truly descriptive names even if they are sometimes long.
- Code must be understandable by reading it. The difficulty of implementing a feature should come from the feature itself, not from unnecessary complexity in the codebase. Document systems whose complexity is inherent and provide enough context for another developer to reason about them.
- Code must behave predictably across different inputs, environments, and failure conditions. Handle errors deliberately. Failures should be contained, understandable, and recoverable where possible.
- Performance matters. Do not waste the user's time or computational resources without good reason. Prefer efficient solutions, but do not sacrifice simplicity or maintainability for meaningless optimization.
- Use the simplest solution that correctly solves the problem. Do not introduce abstractions without a concrete need. If something is inherently complex, do not hide that complexity behind layers of indirection. Keep it visible, structure it clearly, and document what is necessary to understand it. Complexity should be justified by the problem, not created by the implementation.
- Recommend or make a code change only when it solves a concrete problem in the current code. State the problem and its observable impact before proposing the change. Theoretical purity, generalized best practices, personal preference, and the possibility that another design could be narrower or cleaner are not sufficient reasons to change working code.
- Add, remove, or replace dependencies only with explicit user approval. When approval is given, update `allowed-dependencies.json` with `package.json`; the dependency gate requires them to match.
- Run `npm run lint` after every code change. This command is the complete project gate. A code change is complete only when the command passes.
- Before changing an existing feature, run `rg --files docs` and read every document whose filename names that feature or an interacting feature.
- Feature documentation records only current, settled behavior. When a change alters documented behavior, invariants, reasoning, gotchas, or verification, update the matching files in `docs` in the same change.
